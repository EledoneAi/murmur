# Architecture

Murmur links a team's coding agents: Claude Code, Codex, Cursor, OpenCode, Copilot CLI and Gemini CLI. Each person runs a small program on their laptop, and the team runs one hub. There's no central service: whoever deploys a hub owns it, and laptops talk only to their hub.

```
 laptop                                         hub (one or more instances)
┌──────────────────────────────────────┐        ┌──────────────────────────────┐
│ coding tools' sessions               │        │ core: presence, routing,     │
│   │ hooks, session files, inbox      │        │       overlaps, limits       │
│   ▼                                  │  wss   │ web: sign-in, team, admin    │
│ daemon ── ipc socket ── console      │◀──────▶│ dist: install.sh, binaries   │
│   ▲                    └─ mcp (who,  │        ├──────────────┬───────────────┤
│   │                       send, btw) │        │ store        │ bus           │
│   └── update (verifies, swaps, rolls │        │ sqlite · pg  │ local · pg ·  │
│       back)                          │        │ firestore    │ redis         │
└──────────────────────────────────────┘        └──────────────┴───────────────┘
```

| `internal/hub` | The hub: presence across instances (`presence.go`), connections (`links.go`), routing and limits (`route.go`), overlaps, settings, background jobs, and its web side: sign-in and dev login (`signin.go`), the JSON the pages ask for (`/api/...`, the admin panel's under `/api/admin`), the team page's stream, downloads, and the pages themselves, which `web/` builds into `webdist/` and the binary embeds |

Only `cmd/` builds binaries. The other Go packages are `internal/`, so nothing outside this repo can depend on them.

## The hub

### State
- **Durable state** is in the store:
  - people, laptops and their token hashes, with each laptop's version, last sighting and last self-check
  - messages kept for someone offline
  - one-time sign-in codes
  - admin settings
  - announcements to repos, while they are up
  - the admin event log: the newest 10,000 events, none older than 90 days, never message text
  - the newest release the release check found
  - the job lease
  - the weekly counts, team totals only: each instance adds its own under its own key, and the report sums them
  - which waits the chat was pinged about, the collisions counted today, and the last weekly report posted
- **Live state** is in memory:
  - the WebSocket links an instance holds
  - the roster, rebuilt from presence events; overlaps are read from it when a laptop checks files or a roster goes out
  - the team pages open on the instance, each streaming the roster
  - the questions by the way asked on the instance, for a day, answered or not, since a final answer may not have reached the laptop that asked: the laptop that asked each, where its answers go, and the laptop holding the agent, never what was asked
  - rate-limit windows

Mutes are not on the hub: each laptop keeps its own. Neither are questions by the way: the hub passes each question and its answers on, and keeps none of them in the store. Its logs say who asked which agent, never what was asked or answered.

A restart loses nothing that matters: laptops reconnect, say hello again, resend what is in their outbox, and ask again the questions by the way that have no answer yet, saying so (`again`), so a question whose agent's laptop hasn't reconnected yet, or that holds its answer once the agent is gone, waits rather than fails.

### Instances and the bus
- Every instance publishes events to the bus and acts on the events that concern its own links.
- Event kinds:
  - **presence:** a laptop's agents; **alive:** the laptops an instance still holds; **sync:** a new instance asks
    the others for theirs
  - **frame:** a frame for one laptop or for every laptop of one person, held by another instance
  - **changed:** a person, laptop, setting or announcement changed in the store, so reload it
  - **answer:** the answer to a message sent from the team page, for the instance where the page waits
  - **btw:** an answer by the way that reached an instance which doesn't know its question, or passed its final answer on already, for the instance where it was asked. Only a hub with other instances publishes one, and it takes at most 60 such answers a minute from one laptop
- With one instance the bus is in memory, and the code path is the same.
- Postgres's `NOTIFY` takes less than 8000 bytes. The Postgres bus puts a larger event (a long message, question or answer) in its table, `murmur_bus`, notifies its row's id, and deletes rows once they are five minutes old. Redis keeps nothing.
- Each instance says which laptops it holds every 10 s. A laptop no instance has named for 35 s is offline, which covers instances that die without saying goodbye.
- Background jobs run every 30 s on whichever instance holds the job lease in the store: expiring kept messages, the release check (once a day), following the team (waits and collisions, counted for the weekly report, and chat pings about agents left waiting), and the weekly report. Holding the lease is the only form of leadership. The hub schedules nothing on laptops: each one checks its own setup every `check_hours` and reports it.
- GitHub posts pull request events to `/github/webhook`, signed with the team's secret. When one merges, the instance that took the event reads its files from GitHub's API and tells the agents changing them, wherever they are connected.
Ceilings, on purpose:
- Every instance sees every event. A team is a few hundred laptops at most, so that's fine. Partition by person if teams ever get much bigger.
- Every laptop gets the whole team in each roster, so rosters cost the team's size times its laptops. An instance encodes each roster once and hands out at most 128 MB of them a second, in turn: laptops that just said hello first and at twice that, the team pages as one more laptop. A laptop that gets a message gets the roster that has its sender as it was first. The consoles of a big, busy team catch up every few seconds, and its messages keep their speed. Rosters that carry only who changed would lift this ceiling; they need a new protocol.
- Loop limits between two agents, which count their messages and questions by the way, are counted per instance. Agents connected to different instances can exchange up to twice the limit before it trips. So are the questions a person asks by the way in an hour: a person whose laptops are connected to different instances can ask up to the limit on each.

### Configuration

Environment variables only cover what is needed to start: where to listen, the store, the bus, the identity provider, the first admins and the public URL. The allowlist and `TOKEN_DAYS` only seed a new store. Everything a team tunes later lives in the store and is changed in the admin panel without a restart: who may join, sign-in lifetime, limits, ignored paths, update policy and oldest accepted version, laptop checks, the release check, agreements, questions by the way, the team's chat and GitHub merge notices.

## The laptop

The daemon is the only long-lived process. The console, the MCP server, one-shot commands and the coding tools' hooks talk to it over a unix socket. It reads what the tools record and never asks agents to fill anything in. Mutes live in its history on the laptop.

### Harnesses

Each coding tool, a harness, is behind `harness.Harness`: connect and disconnect for join and uninstall, checks for doctor, and reading a hook's input and writing its answer. Hooks run `murmur hook <harness> <event>`, which hands the daemon a `harness.Event` in murmur's words (start, prompt, before-tool, after-tool, stop, needs, end) and prints the daemon's answer in the tool's own dialect. Four optional capabilities, found by type assertion, say what more a tool offers:

- **`Lister`**: the tool keeps a registry of its live sessions, which the daemon watches (Claude Code's `~/.claude/sessions`). Without one, the daemon learns each session from its hooks: the first names it (`codex-1`), a prompt or a tool call means it works, the end of a turn that it waits, and it goes when it ends, when its process does, or after 12 hours without a hook. A hook finds its tool's process by walking up past the shell that runs it. Sessions learned this way are kept in the history, so a restarted daemon knows them again.
- **`Pusher`**: murmur can hand a running session a message (Claude Code's inbox, OpenCode's plugin). Without it, messages wait in a queue per session and leave with the answer to its next after-tool, stop or prompt hook. An idle agent gets them only when its person prompts it again; its sender is told.
- **`Reader`**: the tool's transcripts are worth reading for the title, pull requests, tool calls and context use (Claude Code), the size of the conversation in tokens, the first line of what the agent last said, which only its own person sees and never leaves the laptop, and where its turn stands for a question by the way (a tool call waiting for its result, a reply being written, a result being worked on), which shows nowhere. Without one, tool calls come from the tool's hooks, through one table of every tool's tool names.
- **`Asker`**: the tool can answer a question by the way from a throwaway copy of a session, which the session never sees (Claude Code, which forks a conversation). Without one, the tool's agents can't be asked: their `btw` stays empty in the roster. They can still ask, with the `btw` tool. An `Asker` may also tell a session it doesn't copy (`CopyChecker`: Claude Code before 2.1.292, `claude.AskVersion`, the oldest a copy was checked with), which is then offered to nobody, its `btw` empty, while its person hears why (`murmur btw`, and the console from `cant_ask` in the snapshot); and remove what the copies of a daemon that stopped left behind (`CopySweeper`), as the daemon starts.

Sessions are keyed by harness and session id. The console, the hub and the protocol don't know harnesses: an agent's `App` says which tool it runs in. The MCP server knows which session it speaks for from its parent process, the session id a tool gives it in its environment or in a tool call's metadata, or, failing those, the busy session of its tool.

An agent's repo, branch and change are those of the checkout it works in now, not of the folder it started in. The daemon follows the folder its harness says it works in, from each hook's `cwd` and from Claude Code's transcript, which records it on every line as `cd` and worktrees move it, and the file each edit is about to change, out of its checkout into another. Only a git checkout takes it (`gitscan.TopOf`, which starts no git): a scratch file or a folder outside git leaves it where it works, and so does a subagent's call, which may run in a worktree of its own. A copy answering by the way still runs in the folder the session started in, where Claude Code keeps its conversation. Git is read again as soon as the agent moves, every 20 s while it works, and once more whenever its status changes; a read asked for while another runs, or just after one, follows on the next tick. Its pull request shows while it works in that PR's repo, known by name, since a fork's origin has another owner.

An agent's name is its session's, never a folder's, so its address holds wherever it works. Claude Code names a session after the folder it started in, and says so (`nameSource: derived`): murmur names such a session after its id instead, `claude-0905` (more of the id when another session on the laptop has that name), and keeps a name its person gave it. Claude Code also titles a conversation once, from its first prompt, and the title is how teammates and their agents decide whom to ask. So once git has read where a turn left the session, the daemon checks the title when the work may have moved on: at once when the session works in another repo or on another branch than at the last check, and after a turn its person started (the transcript's `turnOrigin: human`, not a message handed to it), once 10 minutes have passed since the last check. A copy of the conversation, as for a question by the way (`copyOf`, from `murmur`), hears the title showing and answers `KEEP` or a new title of six words at most, which shows until Claude Code or the session's person titles it anew. The turn that just ended warmed the prompt cache the copy reads; each check costs the person about one read of the conversation from that cache, a few cents. A person who turns it off (`murmur retitles off`, `retitles` in the laptop's config) and a session whose copies can't run keep the coding tool's title.

The tools that wait for hooks wait for these, each bounded well under a second:
- **Session start:** the daemon briefs the session: who else works in its repo, the files its checkout shares with another (it asks the hub with `check`) and messages waiting for it, in five lines at most, then the team's agreements, which the daemon keeps from the hub's welcome. The MCP server's instructions carry the agreements too.
- **Before an edit:** the daemon asks the hub whether another checkout of the repo changes the file, for at most half a second, and the first such edit in a conversation is turned back once with the other agent's name.

Any failure prints nothing and lets the session go on.

`murmur solo` sets a laptop up with no team: its daemon runs `internal/hub` itself, on 127.0.0.1, with the memory store, the local bus and no identity provider, so no page signs anyone in. At each start the daemon signs its person in with `Hub.Solo`, under their login name, and saves the token, which only that run's hub accepts. It keeps its port while the port is free. The laptop binary is built with the `laptop` tag, which leaves out the server-only stores and buses (`internal/store/laptop.go`, `internal/bus/laptop.go`).

`murmur join` signs a laptop in with OAuth for native apps and PKCE: it opens the hub's `/cli/login`, and the browser comes back to a one-shot listener on 127.0.0.1 with a code the laptop trades for its token. Over SSH, or with `--no-browser`, it prints a link to `/cli/login` with port 0 instead: the page shows the code, and its person pastes it into the terminal. Only the laptop that started the sign-in can trade the code.

### Questions by the way

A person asks an agent something by the way from the console or with `murmur btw`, and an agent with its `btw` tool; either hands the daemon the question over the socket (`btw`, then `btw-wait` for the answer). A throwaway copy of the agent's conversation answers it on the laptop of the agent's person. The agent never sees the question: nothing goes to its inbox, it takes no turn, and its context doesn't grow.

- **Where it runs.** A question from a person, or from one of their agents, to one of their agents on the same laptop never leaves it: the daemon runs the copy itself. Any other goes through the hub to the laptop that holds the agent, as [Protocol](#protocol) says, and the answer comes back the same way. On a laptop on its own (`murmur solo`), whose hub is its daemon's and holds nobody else, the daemon refuses any other question at once, saying that a teammate's agent needs the team's hub.
- **Agents asking.** The MCP server's `btw` tool, and OpenCode's plugin through `murmur tool opencode btw`, name the session they speak for, as `send` does, and the daemon asks as that agent: `from` is `alice/main-1`. The tool waits 50 seconds at most, under every coding tool's time limit for a tool call, Codex's minute being the shortest, and the daemon answers its `btw-wait` within 45 seconds: the answer, in the envelope a hook's message comes in, or where the question stands. Why there is no answer, and where the question stands, may come from the hub or the laptop holding the agent asked: the tool quotes them, on one line, as relayed by murmur, never in its own words. A final answer no `btw-wait` returned goes to the asking agent once, through the usual delivery (its inbox, the plugin, or a hook's answer), as a message from the agent asked under the ID `bw-<question ID>`; with no answer, as murmur's own note, quoting why, which waits while the agent is idle. Either ends with a footer of its own in place of a message's, which would have the agent answer the agent asked with `send`: it says the answer came, through murmur, from a copy of that agent's conversation, that the agent itself never saw the question, and to follow up with `btw`, keeping `send` for when that agent must act or reply itself. A tool call the coding tool cancels (MCP's `notifications/cancelled`, OpenCode's abort signal, as its person stops the agent) closes its `btw-wait` at once, and gets no answer; the daemon hands an answer only to a `btw-wait` still there to read it, and one it couldn't goes as that message. A delivery that fails goes again every two minutes while the agent runs, for an hour at most (an inbox that refuses it, a Claude Code too old to take messages, would refuse it forever), and only in memory: the history records the question once. An agent that closes first gets nothing, and its laptop stops asking. One that closes with the answer still waiting for its next hook drops it, telling nobody: the agent asked never wrote that message, nor saw the question, and the note a sender gets for a message its agent never read would quote it. The hub refuses messages from laptops under `bw-` IDs, as it does under its own `gh-` and `an-`. The console shows the delivered answer once, as the question's, knowing it by its ID alone, and links the two agents on the board, as a message does.
- **What waits.** The answering daemon decides from its person's setting (`btw_answers` in its config: `approve`, the default, `auto` or `off`) and the agent's state, and treats a teammate's agent as the teammate. With `off`, its agents say `mine` in the roster, and teammates and their agents are refused, by the hub and by the daemon. A teammate's question to a cold agent, whose transcript hasn't been written for over an hour while its session isn't busy, waits for its person's go before the copy runs, even with `auto`: the prompt cache is gone, and a copy would read the whole conversation again at full price. The person sees how much it would read, the size of the conversation at its last request. With `approve`, the copy runs at once and its answer waits for the person. The console says yes or no to either over the socket (`btw-approve`, `btw-decline`), and yes to an answer only once all of it has been on its screen; the plain mode prints it whole wherever it numbers it. The person's own questions and their agents', from any of their laptops, never wait: the daemon reads the person from `from`. The copy hears who asks: "alice's agent main-1", or "your person's agent main-1".
- **Limits.** A laptop answers at most 20 questions an hour from teammates and their agents, whatever the hub allows: the copy is billed to its person, and the hub isn't trusted with their spending. It runs at most two copies at once, one per session. Two more questions for a session wait for its copy, five minutes at most, and one more is refused. A copy has two minutes to answer. The hub counts each question it carries against the person who asks, their agents' with theirs (`btw_per_hour`), and against its sender, person or agent (`sends_per_minute`); a question between two agents also counts toward their loop limit (`loop_max` in `loop_minutes`), with their messages either way. A question answered on the laptop it was asked from never reaches the hub, and counts in none of these. The daemon stays up while a question asked from its laptop waits for its answer, a day at most, as it does for a session or a console: it alone hears the answer. When it stops (replaced by a newer murmur, uninstalled, `SIGTERM` or `SIGINT`), it stops the copies running first, with their process groups, waiting a few seconds at most: a copy left running would answer nobody, at its person's cost. Their questions stay running in the history, and the next daemon fails them, saying murmur restarted. As it starts, it removes the settings files those copies left in murmur's folder, which hold sign-in, unless their copy still runs (a daemon killed outright doesn't stop its copies); the next copy removes those over an hour old.
- **The copy.** Claude Code's `Asker` runs `claude -p --resume <session> --fork-session` in the session's folder, for a session of Claude Code 2.1.292 or later (`claude.AskVersion`, as its registry entry says), which has every flag below, runs `PreToolUse` hooks from `--settings`, and writes the endings the framing explains; the nightly compatibility check runs a copy on the newest Claude Code ([development.md](development.md#claude-code-compatibility)):
  - with the session's own `claude`, the binary its process runs (from the process's arguments on macOS, `/proc/<pid>/exe` on Linux; for an npm install, its JavaScript runtime with Claude Code's script), since the daemon's `PATH` may not have one and the desktop app bundles its own. The daemon reads the process's start time when it takes a session in, and compares it with the one Claude Code recorded in the session's registry entry (`procStart`, to the second); the copy takes anything from the process only when they agree and while its start time is the same, so a PID the system gave another program, before the daemon took the session in or since, is never trusted. Otherwise the copy runs the `claude` on the `PATH` or where the installers put it. The copy keeps the session's model.
  - as a fork, under a session id the daemon chooses before it starts, which the session scan skips, so the copy never shows as an agent. It saves nothing (`--no-session-persistence`): the session's transcript stays byte for byte as it was, and the daemon removes the empty folder the copy may leave in Claude Code's `session-env`.
  - with no tools: a `PreToolUse` hook, passed with `--settings`, refuses every call, whatever the allow rules say, and adds a line to a file in murmur's folder each time it runs. The session's tools stay declared, since dropping them would rewrite the whole conversation into the prompt cache at many times the price. `--setting-sources ""` loads none of the person's settings files, so none of their hooks, allow rules or MCP servers; managed settings still apply. Managed settings that say `disableAllHooks` or `allowManagedHooksOnly` would keep the hook from running, and the copy could then read files (`dontAsk` still lets it read): before each copy, Claude Code's `Asker` reads them where Claude Code 2.1 does (`managed-settings.json` and the `.json` files of `managed-settings.d` in `/Library/Application Support/ClaudeCode` on macOS and `/etc/claude-code` on Linux, the Mac's configuration profiles `com.anthropic.claudecode` through `plutil`, the organisation's settings from claude.ai that Claude Code keeps in `remote-settings.json`, and the folder and file `CLAUDE_CODE_MANAGED_SETTINGS_PATH` and `CLAUDE_CODE_REMOTE_SETTINGS_PATH` name), and when any says either, it runs no copy and says why. The daemon checks them too, at most once a minute, before it tells the team its agents can be asked: their `btw` stays empty. After a copy, a turn more than the tool calls the hook counted (each turn after the first follows a tool call) means a tool ran that the hook never saw: the answer is dropped, and the copy fails. Claude Code's `permission_denials` doesn't tell, as it leaves out the calls a hook refuses. The copy's environment has `MURMUR_BTW` set: murmur's own hooks, MCP server and tools, should anything start them in a copy, do nothing.
  - signed in as the session: the daemon reads the session process's environment when it asks, keeps only the provider settings (Bedrock, Vertex and the other providers, API keys and base URLs, AWS and Google Cloud credentials and regions, proxies and CA certificates) and passes them to the copy, never storing, logging or sending them. Nothing else from that environment reaches the copy, Claude Code's messaging token least of all. When it can't read it, the copy keeps none of the daemon's own provider settings, which came from whichever session started the daemon, but its proxies and CA certificates: it signs in as Claude Code does without them, with the keychain, the person's settings and managed settings. The `env`, `apiKeyHelper` and `awsCredentialExport` of the person's `settings.json` go into the `--settings` file beside the hook, which only the person can read, in murmur's folder, and which goes with the copy: on the command line they would show to every user of the laptop. Never the commands that open a browser to sign in, and never a project's settings, which would get around Claude Code's folder trust.
  - with the question on stdin, framed: who asks, and what the agent is doing now, from where its turn stands in its transcript ("in the middle of Running go, waiting for its result", "writing its reply to the last message in this conversation", "working on the result of Reading api.go", "idle for 3h"). A copy of a busy session finds its last turn cut short, with a "[Tool call interrupted…]" result for a call in flight or "No response requested." for a reply being written: the framing says these come from making the copy, that the work goes on, and that asked what it is doing, the copy describes that work. The prompt starts with murmur's words, where Claude Code would read a command (`/`, `!`, `#`), and every `@` in what others wrote is followed by a space: Claude Code attaches a file the prompt mentions (`@path`) before any tool runs, out of the hook's reach.
  - in a process group of its own, killed once the copy is done or stopped, with anything it started.
  - with bounds on cost, not safety controls (the hook is): `--max-turns 4`, as the copy answers in one turn, or two when it tries a tool and the hook refuses it, and a spending cap (`--max-budget-usd`) sized to the conversation, from the tokens its last request sent: one full cache write at $25 a million tokens, above any model's price, plus four reads at a tenth of that, $5 at least. Claude Code checks the cap after it has paid for a turn, and then gives no answer, so a cap below one turn's cost would throw the answer away: this one stops only a runaway copy. The daemon reads the answer and the tokens the copy read (input, cache creation and cache read) from `--output-format json`.
- **Failures** stay on the laptop that ran the copy. A sign-in failure says what the agent's person can do: `aws sso login`, `gcloud auth application-default login`, or log in to Claude Code. Any other failure of the copy says what Claude Code said (its paths, its output, a provider's error). A teammate, or a teammate's agent, hears only that the copy couldn't sign in, or failed, and that the agent's person sees why; what murmur says of a question it doesn't take (the agent closed, too many questions waiting) reaches them as it is.

## Updates

- **We** publish signed releases and nothing else: binaries, hub images, and `checksums.txt` signed into `checksums.txt.sig` with the project key. The release workflow builds the public key into every binary and stops when it is missing.
- **The admin** chooses when the team moves, by upgrading the hub. Each hub image carries the client binaries of its own version, so a hub needs no internet access to serve updates. The admin panel can check for new releases once a day, and the admin can switch that off.
- **The hub** tells each laptop the team version, the oldest version it accepts, and the team's update policy: `auto`, `notify` or `off`. A laptop older than the oldest accepted version is refused, with the command to run.
- **The user** can run `murmur update` at any time, and set their own laptop to `ask` or `off`. A refused laptop updates itself whatever the policy, unless its person chose `off`: then it stays refused until they run `murmur update`.
- **Verification:** laptops verify `checksums.txt.sig` against the key built into the binary, then the checksum of what they download. A hub can't update laptops to code the project didn't sign. A binary built without a key checks the checksum only. The install script checks the binary against the hub's `checksums.txt`, not the signature: a first install trusts the hub over HTTPS. A hub built with a key refuses to start when its `DIST_DIR` holds binaries the key didn't sign. A team that builds from source builds in its own key.
- **Applying an update:** when an update is due and none of the laptop's agents is busy, the daemon starts `murmur update --auto` in a child process, at most once an hour. The child downloads and checks the binary, replaces the running one in place and keeps the old one as `murmur.prev`, then restarts the daemon and waits up to a minute for it to be online on the new version. If it isn't, the child puts `murmur.prev` back and restarts the old daemon, and automatic updates skip that version for an hour; `murmur update` run by hand tries it again. Laptops never move to an older version because a hub says so.
- **Package managers:** binaries that Homebrew or Nix installed (under `/opt/homebrew`, `/usr/local/Cellar`, `/usr/local/Caskroom`, `/home/linuxbrew` or `/nix/store`) never replace themselves. They say which command to run. Their hooks and MCP server point at the package manager's link on `PATH`, which stays valid across upgrades.

## Protocol

Frames are JSON objects over one WebSocket per laptop. `hello` carries the protocol version. A hub refuses protocol versions it doesn't speak, with a message that says what to update. There is no compatibility with releases from before 1.0.

Beyond the version, a laptop's `hello` and the hub's `welcome` list in `can` what each side carries: `btw`, for questions by the way. Neither side sends a frame the other didn't list: an older peer would drop it, and the asker would wait for nothing. For the same reason a question is never a kind of message: an older laptop would hand it to the agent. Each agent in a roster says in `btw` whether teammates and their agents can ask it and how its person answers, `approve` (each answer waits for them) or `auto`; `mine` when its person turned teammates' questions off, and only they and their agents ask it (an older laptop reads `mine` as empty). It is empty when nobody can ask it through the hub: its tool has no `Asker`, or can't copy this session (an older Claude Code, managed settings that turn hooks off), or its laptop or the hub doesn't carry questions. The hub clears it for a laptop that doesn't, and when its admins turn questions off.

A question by the way takes two frames, each with a `btw` object:
- **`btw`**, from the asking laptop to the hub: an ID the laptop chooses, the agent asked (`to`), the question, and, for an agent's question, the agent that asks, in `from` as `person/agent`. The hub writes `from` itself: the handle of the laptop's person, whatever the laptop wrote, and the agent only when that laptop runs an agent of that name; otherwise it refuses the question. It counts the question against the asker's limits (`btw_per_hour` for the person, their agents included; `sends_per_minute` for the person or the agent; the loop limit between two agents), and passes it to the laptop that holds the agent, through the bus when another instance holds it. Otherwise it answers at once with why not, in a final error: the agent isn't running or can't be asked (its `btw` is empty, or `mine` for anyone but its person and their agents, even for a question a laptop says it asks again), its laptop runs an older murmur, a limit is reached. A question refused as it is asked again is forgotten at once, however the laptop wrote the agent. While the agent's laptop is reconnecting, a note says so instead. A question the hub knows, asked again, goes to the laptop it went to, even once the agent is gone and once its final answer has gone, which may not have reached the asking laptop, without counting again, and while that laptop is away a note says so. It goes at most once a minute between the same connections of the two laptops (the asking laptop asks again every two minutes and on each new connection, and a laptop holding the agent that connected again may have an answer that didn't leave it): the answering laptop answers each from its history, and a laptop asking one question over and over would otherwise fill its answers. The hub never keeps a question for a laptop that is offline. With `btw` off in the admin settings, the hub's `welcome` doesn't list it, and the hub refuses every question.
- **`btw-answer`**, from that laptop back through the hub to the asking laptop: notes on where the question stands first ("answered; waits for bob to share it"), then one final frame with the answer and the tokens the copy read, or an error. The hub takes at most 60 notes a minute from one laptop, and apart from them 60 answers to questions it doesn't know or passed a final answer for already; the final answer to a question it sent that laptop always passes, one each time the question went. So the notes a laptop sends again for every question asked again never crowd out the answers its person shares.

The asking laptop asks again under the same ID after each reconnection and every two minutes while it has no final answer, for 24 hours at most: the laptop holding the agent may have been away, or restarted before its answer left. It marks a question that went to a hub before with `again`. A hub instance that doesn't know that question, having restarted since or the asking laptop having moved to it, doesn't count it again, though it still checks that the agent's person lets teammates ask it: it was counted where it was first asked (a person's laptops may say `again` of as many questions an hour as `btw_per_hour` allows; past that, they count). When the agent runs, the question goes to its laptop. When it doesn't, the hub asks each laptop of the agent's person again, marked `again`, and answers with a note, never a final error ("bob's laptop is away; murmur asks again until it is back" when none is online): their laptop may not have reconnected yet, or may hold the answer once the agent is gone. A laptop that has seen the question answers it; one that hasn't, and doesn't run the agent, says nothing. The answering laptop knows a question it has seen by its ID and a digest of who asks, the agent and the question, and answers it again from its history: one question never runs the copy twice.
